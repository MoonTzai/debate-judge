# Support and Governance

The initial public project is expected to be maintainer-led. Governance should reflect actual practice rather than imitate a large project.

## Development practice

After publication, substantive changes should be traceable through commits, changelog entries, tests, and public issue/discussion records where appropriate. Single-maintainer development is acceptable; fabricated contributors, pull requests, issue history, or backdated public activity are not.

## Support

Once a public GitHub repository exists, normal bug reports and feature requests may use its issue tracker. Reports should include the software version, environment, minimal reproduction, expected/observed behavior, and whether external model calls were involved. Do not post API keys, private transcripts, or private adjudication artifacts.

## Decision authority

Software-integrity checks can fail closed on malformed artifacts or broken contracts. They must not be used to mechanically erase semantically valid debate-analysis content merely because it does not fit an incidental formatting convention. Semantic and scientific questions remain subject to explicit review and evidence.

## Security/privacy

Credential exposure, personal-data leakage, or rights concerns should be treated as release blockers. A future public security contact/mechanism should be added once the repository identity and maintainer contact channel are finalized.
